## 3. New Defects / Open Questions Discovered at Bench

### 3.1 B-1 — Noise spikes on CKP output (open question, hardware/analog)

**Symptom:** With the generator running, the oscilloscope shows a correct CKP square-wave pattern, but at times severe spikes ride on top of the signal (both levels).

**Preliminary engineering assessment** (full analysis tasked to the next plan):
- The switching mechanism itself — `gptimer` alarm ISR → `dedic_gpio_bundle_write()` — produces single clean CMOS rail-to-rail transitions per slot. It has no inherent mechanism to produce mid-level spikes; it is *unlikely* to be the cause.
- Leading candidate causes, in order of likelihood:
  1. **Measurement artifact** — long scope ground-lead inductance ringing on fast (≈1–2 ns) ESP32-S3 edges.
  2. **Board-level coupling** — the JC4827W543 runs a 32 MHz QSPI LCD bus and OPI PSRAM continuously while LVGL refreshes at ~30 FPS; ground bounce / supply transients couple into adjacent header pins. GPIO 17 shares the header region with other signals.
  3. **Unterminated line** — fast edges into a long bench wire reflect (overshoot/undershoot), reading as spikes.
- Candidate mitigations to be evaluated in plan 3: scope ground-spring instead of alligator lead; 33–100 Ω series resistor at the pin; `gpio_set_drive_capability()` reduction; shielded/twisted output leads.

### 3.2 B-3 — Filter textarea has no input method (major, UI)

`ta_pattern_filter` (`lib/ui_lvgl/ui_lvgl.cpp:695`) is a one-line LVGL textarea wired to `on_pattern_filter_changed` → `rebuild_pattern_dropdown_options()`. The filtering pipeline behind it is implemented and functional — but on this touch-only device there is **no `lv_keyboard` anywhere in the project**, so the textarea can never receive characters. Tapping it focuses the widget and nothing else happens.

Additionally the current match is a plain case-insensitive **substring** scan (`name_matches_filter`, `ui_lvgl.cpp:1111`), not the fuzzy match requested for the next cycle.

### 3.3 B-4 — WAVE overlay: StoreProhibited panic (critical, UI)

**Symptom:** Tapping WAVE opens the overlay, a partial waveform draws, then the firmware panics and reboots to the home screen.

**Serial evidence (3 identical panics captured):**

```
Guru Meditation Error: Core 1 panic'ed (StoreProhibited). Exception was unhandled.
PC=0x42077de6  A2=0x00000000  EXCVADDR=0x00000000
  #0 lv_memcpy           lvgl@9.2.2/src/stdlib/builtin/lv_string_builtin.c:94
  #1 lv_draw_line        lvgl@9.2.2/src/draw/lv_draw_line.c:68
  #2 on_wave_tick        lib/ui_lvgl/ui_lvgl.cpp:1629
  #3 lv_timer_exec → lv_timer_handler → ui_task_handler → loop()
```

**Root cause — confirmed by code inspection (high confidence):**

1. `on_wave_tick()` (`ui_lvgl.cpp:1574`) renders the waveform by issuing **one `lv_draw_line()` per segment** inside a single canvas layer: up to ~440 visible slots × 3 lanes × 2 segments (vertical edge + horizontal level) ≈ **2,600 draw tasks queued per 50 ms frame** before `lv_canvas_finish_layer()` ever executes them.
2. In LVGL 9.2.2, each `lv_draw_line()` call allocates a `lv_draw_task_t` plus a line descriptor from the **builtin LVGL pool** — which `include/lv_conf.h:56` caps at **`LV_MEM_SIZE = 64 KB`** (`LV_USE_STDLIB_MALLOC = LV_STDLIB_BUILTIN`). ~2,600 tasks × ~150 B ≈ 400 KB demanded from a 64 KB pool.
3. `lv_draw_line()` (vendored source, `lv_draw_line.c:66-68`) does:
   ```c
   lv_draw_task_t * t = lv_draw_add_task(layer, &a, LV_DRAW_TASK_TYPE_LINE);
   lv_memcpy(t->draw_dsc, dsc, sizeof(*dsc));   // ← no NULL check
   ```
   When the pool exhausts mid-frame, the allocation inside `lv_draw_add_task` returns NULL and the `lv_memcpy` stores through address 0 — exactly matching `A2=0x00000000`, `EXCVADDR=0x00000000`, and the "partial waveform then crash" symptom.
4. The active pattern (`toyota_4AGE_CAS`) renders enough segments to exhaust the pool within the first frame or two. Sparser patterns would survive longer but the design fails for any non-trivial pattern.

**Fix direction (for plan 3):** restructure `on_wave_tick` so per-frame draw-task count is bounded (decimate to ≤1 column per pixel, coalesce runs into single horizontal segments, and/or render via direct canvas pixel/buffer writes), rather than just enlarging `LV_MEM_SIZE` — the current worst case exceeds any feasible pool.

**Secondary observation:** each panic also logs `esp_core_dump_flash: Core dump flash config is corrupted! / No core dump partition found!` — `partitions_signalgen.csv` has no `coredump` partition. Cosmetic during normal operation, but it cost us the post-mortem ELF for the first crash. Optional hardening for a later cycle.
