## 0. How to use this artifact

Each verification item below carries a **`RESULT →`** line. After you exercise the item on the
bench, **edit that one line in place** to exactly one of:

- **`Confirmed`** — observed behavior matches the *Expected* text verbatim. Nothing more needed.
- **`User notes: <your observation>`** — anything else: a deviation, a bug, a scope reading that
  is off, a crash, a UX nit, or a "works but…". Be concrete — name the channel/step/value you
  used, what you saw vs. expected, and (if you can) the RPM/pattern in play. These notes become
  the work-list for the next development cycle.

Leave the leading placeholder token (`Confirmed` / `User notes:`) so the orchestrator can machine-scan
the file. Do **not** delete items you skip — set them to `User notes: skipped (reason)` instead, so
nothing is silently dropped.

Each item has a stable ID (e.g. `C6-V1`, `C6A-V4`). Reference these IDs when you discuss results.

## A — Cycle 6: Firmware RPM crank-fix

> **What cycle 6 changed:** `TableCkpGenerator::reprogramAlarm` now scales the per-slot period by the
> table's degree span — `period_us = 60000000 * _table_degrees / (360 * rpm * slot_count)` — so the set
> RPM is always the **crank** RPM. A 720° table (crank internally doubled when any cam is present) used
> to run the crank at 2×; it now runs correctly, and the cam at half-crank.
>
> **These items can be checked on HEAD (`2d43a18`) or on the RPM-only fallback (`dca84e6`).** The fallback
> is byte-identical in RPM behavior but still has the *old* UI (pre-6.a), so use it only if you want to
> isolate the RPM fix from the new Custom tab.

### C6-V1 — RPM headline (the bug that was fixed)
- **Setup:** base RPM **800**. Scope the CKP output (GPIO 17) and the CMP1 output (GPIO 9).
- **Do:** (a) select a **CKP-only** pattern (e.g. `sixty_minus_two`); (b) select a **CKP+CMP** 720°
  builtin (e.g. `sixty_minus_two_with_cam`).
- **Expected:** (a) CKP measures **800 RPM**. (b) CKP measures **800 RPM** (previously **1600** — this
  was the reported doubling bug) and CMP measures **400 RPM** (cam = ½ crank, physically correct).
- **RESULT →** `User notes: <fill in — include the two measured CKP values and the CMP value>`

### C6-V2 — 720° crank-only builtins now run half-rate
- **Setup:** base RPM 800.
- **Do:** select `dizzy_four_trigger_return`, then `buell_oddfire_cam` (both tagged 720° in `ardustim.ino`).
- **Expected:** each now plays at **half** the pre-cycle-6 rate (the 720° span is honored). Confirm this
  is the **intended** behavior for these patterns.
- **RESULT →** `User notes: <confirm intended, or note if either should be 360°>`

### C6-V3 — Compression dips land at the correct crank angle
- **Setup:** enable compression on a 720° pattern; pick a known cylinder/peak.
- **Expected:** the compression dip(s) occur at the same crank angle(s) as before the fix (the dip timing
  is ratio-based and proven invariant to the period scaling — bench-confirm only).
- **RESULT →** `User notes: <confirm dip angle vs. expected; note the 0–360-over-720 mapping if relevant>`

### C6-V4 — Sweep unaffected
- **Setup:** configure a sweep (low→high RPM) and START.
- **Expected:** the ramp behaves exactly as before cycle 6; no timing regression, smooth low→high.
- **RESULT →** `User notes: <confirm or describe any timing change>`
