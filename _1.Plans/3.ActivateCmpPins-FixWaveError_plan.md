## 4. Noise-Spike Verdict (R1) — Answer to the User

**Question:** *Are the spikes riding on the CKP square wave normal, or are they produced by our switching mechanism?*

**Verdict: Predominantly normal — a measurement artifact plus board-level coupling. The gptimer/dedic_gpio switching engine does not corrupt the signal. One honest nuance: the ringing visible at the transitions is excited by our (default, strong) output edge — which is why a drive-strength reduction is included this cycle.**

### Why the switching engine cannot glitch a held level

- The ISR (`TableCkpGenerator::onAlarm`) executes `dedic_gpio_bundle_write(...)` on **every** 1 MHz tick, even when the byte hasn't changed (`TableCkpGenerator.cpp:419,427,431`). On the ESP32-S3, that write lands in an output register/pad latch holding a **static level**; re-writing the *same* value produces no edge, no charge/discharge event — it is physically incapable of injecting a spike on top of an already-held plateau. (The redundant write merely costs a few CPU cycles; not worth changing, §8.)
- The playback path is fully deterministic (fixed alarm period, memcpy'd internal-DRAM table, idempotent write) — it has no state that would make spikes "come and go." The cycle-timestamp publish on wrap (`:434,438`) never touches pins.

### The nuance — edge-correlated ringing IS partly ours

Spikes clustered **at the transitions** (overshoot/undershoot decaying into each plateau) are ringing excited *by our edge*: `begin()` never sets drive strength, so pins run at the chip default `GPIO_DRIVE_CAP_2` (~20 mA — the *medium/default* setting; CAP_3 ≈ 40 mA is the strongest) with a ~2-4 ns native edge. That fast edge into an unterminated bench lead + long scope ground clip is a textbook LC-ringing recipe. The signal *logic* is correct; the *excitation* is reducible from firmware — hence work-package A1.

### Ranked causes

1. **Most likely — scope ground-lead ringing:** a ~6 in alligator ground clip (~100-200 nH) + probe capacitance forms an LC tank ringing at hundreds of MHz when hit by a ns-scale edge; appears as decaying spikes on both plateaus right after each transition. Pure measurement error.
2. **Secondary — board coupling:** the 32 MHz QSPI LCD bus, OPI PSRAM, and backlight boost converter all switch hard on one small module sharing the 3V3 rail/ground; activity couples into the unshielded flying lead. Explains spikes *between* transitions and "at times" intermittency tracking LCD redraw bursts.
3. **Possible — reflections** off the unterminated bench wire.
4. **Unlikely to dominate — USB CDC** hash.

### Bench falsification tests (user; no firmware needed)

1. **Ground-spring test** — swap the alligator ground lead for a short ground spring at the probe tip. Spikes shrink dramatically → probe ringing (artifact).
2. **LCD-correlation test** — open the PATTERN dropdown / drag the RPM arc while watching the trace. Spike amplitude tracks LCD activity → board coupling.
3. **Stopped-output test** — `stop()` parks the bundle low (`TableCkpGenerator.cpp:382`); with the generator STOPPED and the LCD refreshing, any residual spikes are conclusively coupling/probing, not the switching engine.
4. **Probe-move test** — reposition probe and ground return; if the spikes change shape/amplitude, it's measurement.

**Bench wiring guidance:** short ground spring; if hardening the output for real harness use, a 33-100 Ω series resistor at the pin (source termination) — apply **one** mitigation at a time and re-measure (don't stack blindly with the CAP_1 change).

## 5. Agent Work Packages

### Agent A — Backend (`gen-backend`)

**File edited:** `lib/ckp_gen/TableCkpGenerator.cpp` (only)
**Requirement:** R1 firmware mitigation

**A1 — Lower output drive strength.** In `begin()`, immediately **after** the `gpio_set_level()` init block (`:177-179`) and **before** `dedic_gpio_new_bundle()` (`:186`):

```cpp
// Lower output drive strength to slow the native edge rate, reducing
// scope-ground-lead ringing and EMI coupling on the bench, without
// changing the logical waveform or timing.
// NOTE: chip default is GPIO_DRIVE_CAP_2 (~20 mA — the medium/default
// setting; CAP_3 ~40 mA is the strongest). The SDK enum names
// (weak/stronger/medium/strongest) are misleading; numerically
// 0<1<2<3 = ~5/10/20/40 mA. CAP_1 (~10 mA) therefore LOWERS drive
// vs default while keeping a crisp 0/3.3 V swing into a high-Z input.
static constexpr gpio_drive_cap_t kOutputDriveCap = GPIO_DRIVE_CAP_1;
gpio_set_drive_capability((gpio_num_t)_pin_crank, kOutputDriveCap);
if (width >= 2) gpio_set_drive_capability((gpio_num_t)bundle_pins[1], kOutputDriveCap);
if (width >= 3) gpio_set_drive_capability((gpio_num_t)bundle_pins[2], kOutputDriveCap);
```

`driver/gpio.h` already included (`:16`); signature `gpio_set_drive_capability(gpio_num_t, gpio_drive_cap_t)` confirmed in the vendored ESP-IDF headers. Ordering-safe: drive capability is a pad property independent of dedic_gpio matrix routing. Chosen `CAP_1`, not `CAP_0`: ~5 mA can sag/over-round into capacitive loads or longer cables; ~10 mA meaningfully slows the edge while preserving a clean swing. Single named constant so the user can retune in one place.

**No interface change** — `CkpGenerator.h` stays byte-identical; legacy `TimerCkpGenerator` untouched.
